The problem

Executives ask the data team the same twelve questions every week, and the data team answers them by hand. The tools meant to fix this fail two ways in any serious environment:

  • The model can reach whatever the credential can reach. One prompt away from every table in the warehouse, including the ones with personal data in them.
  • A wrong answer looks exactly like a right one. The prose is fluent either way, so nobody can tell which number to trust — and therefore nobody trusts any of them.

How this is different

A table you don't publish does not exist

The semantic layer is the contract. The demo warehouse contains an employee_salaries table with 50 rows in it. Ask for it:

# the table is real — same database the query engine has open
$ SELECT COUNT(*) FROM employee_salaries
(50,)

# but it was never published to the semantic layer
$ ask "show me employee salaries"
REFUSED — blocked at stage 1 · no SQL generated · no connection opened

Not a blocked keyword. The table is invisible, and any query naming it is rejected by an AST-level validator before execution. Nineteen hostile queries test this on every commit.

It refuses instead of guessing

"what is the weather in Hyderabad"  →  REFUSED (out of scope, stage 2)
"how many invoices in 2012"         →  zero rows, and it says so — not a fabricated number

An earlier version answered the weather question with total revenue: valid SQL, real number, wrong question. That class of failure is worse than a crash because nobody notices it. Refusing is the behaviour that makes the rest of the output worth acting on.

Every number is auditable

Each answer carries the SQL that produced it and a seven-stage trace. The audit log records every question — answered or refused — with who asked and which stage blocked it.

14:55:29  field_officer  refused   blocked=intent_detection   show me employee salaries
14:55:29  field_officer  answered  rows=10                    highest revenue products last quarter

Nothing has to leave your estate

Runs against a self-hosted model (Ollama, vLLM, Databricks) or with no model at all, using a deterministic planner. A configured local endpoint overrides any API key, so a forgotten environment variable cannot leak prompts. /health tells an operator which is live.

Metrics are defined once

"Revenue" means the same here as on the dashboard, because both read the same certified definition — including its mandatory filters. Nobody asked for WHERE status NOT IN ('cancelled','returned'); it travels with the metric.

What it does, end to end

Question → Intent detection → Schema retrieval (RAG) → SQL generation
         → AST validation → Read-only execution → Result validation → Answer + chart
StageWhat it stops
Intent detectionWrite requests, restricted-data fishing, prompt injection
Schema retrieval + scope gateOff-topic questions; the model seeing tables outside the contract

Getting it onto your data

$ ai-analyst init --url "snowflake://readonly@acct/db/schema"   # or --dbt manifest.json
  Read 11 tables. Fact tables: Invoice, InvoiceLine · 9 joins inferred
  17 columns flagged as likely personal data
  Wrote draft semantic layer.

$ $EDITOR semantic_layer.yml     # the one human step: ~1 hour
$ ai-analyst check                # every entity and metric executes
$ ai-analyst serve

It introspects your warehouse or dbt project, classifies columns, infers joins, flags likely personal data and drafts your metrics — every one marked REVIEW, because SUM(unit_price) is meaningless and metric definitions are your decision, not the tool's. Warehouses: DuckDB, PostgreSQL, Snowflake, BigQuery, Databricks, MySQL, Redshift, Trino.

After go-live, an analyst edits metric definitions through a form in the UI. Changes are validated against the warehouse, backed up, applied without a restart, and audited with a diff that flags any newly exposed table or column.

Evidence, not adjectives

Tested against a schema it had never seen

Pointed at an 11-table open-source database, it surfaced six of its own bugs in ten minutes — all documented, all fixed. No guardrail was breached in the process.

CI proves the claims on every commit

Runs with no model at all

A deterministic planner answers the common questions. That is how the test suite runs — offline, no API key, no network.

Deployed and reachable

Honest limitations

  • The semantic layer needs about an hour from someone who knows the data, per warehouse. That is the real work, and no tool removes it.
  • Complex analytical questions — cohort retention, attribution, window functions — are outside what it writes today.
  • Accuracy is a property of your metric definitions. The semantic layer makes them reviewable; it does not make them correct.
  • It answers questions about data you have already modelled. It is not a data catalogue and will not rescue a warehouse nobody understands.
